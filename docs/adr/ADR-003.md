# ADR-003 - Protocolo de Comunicação em Tempo Real para Atualização de Dashboards

## Status
Aceito

## Contexto
O edital do desafio técnico (Seção 2.5 e requisito RNF002) impõe uma restrição de sincronismo visual crítica: quando o médico Especialista registra um parecer técnico, a interface do Solicitante (na Atenção Primária à Saúde) deve refletir essa mudança imediatamente, em tempo real, sem qualquer necessidade de recarregar a página (refresh do navegador).

No cenário atual analisado, o fluxo de atualização é passivo e ineficiente, exigindo que o usuário envie requisições manuais repetidas para verificar se houve resposta. Precisamos definir uma tecnologia de comunicação atrativa e assíncrona para implementar o modelo de empurrão de dados (*server-push*) do backend Django para o frontend Next.js, mantendo a latência mínima e sem inflar o consumo de requisições no banco de dados PostgreSQL.

## Decisão
Decidimos adotar o protocolo **WebSockets** de comunicação bidirecional e persistente, utilizando a seguinte arquitetura de implementação:

1. **Backend (Django Channels):** Extensão do ecossistema síncrono padrão do Django para uma arquitetura assíncrona (ASGI), capaz de gerenciar conexões persistentes de WebSockets de forma nativa através de *Consumers*.
2. **Camada de Transporte (Redis Channel Layer):** Utilização do Redis operando como um *backbone* de mensageria no Docker Compose para gerenciar os grupos de canais e rotear as transmissões (*broadcasts*) de eventos entre diferentes instâncias do servidor.
3. **Frontend (Contexto React/Next.js):** Criação de um custom hook ou provedor global de WebSocket que estabelece a conexão logo após a autenticação segura (JWT) do usuário, escutando eventos específicos de alteração de status baseados no ID do usuário ou do caso clínico.

### Alternativas Descartadas
* **HTTP Short Polling (Requisições Cíclicas):** Descartado pois o ato do frontend disparar requisições `GET` a cada poucos segundos gera uma sobrecarga imensa no servidor e no banco de dados com dados repetidos, além de introduzir uma latência artificial aceitável que fere a premissa de atualização imediata exigida pelo consórcio LAVID/RNP.
* **Server-Sent Events (SSE):** Embora o SSE seja uma alternativa viável para fluxos estritamente unidirecionais (servidor para cliente), foi descartado devido ao planejamento de longo prazo do ecossistema ReNTAI. A escolha por WebSockets deixa a infraestrutura de comunicação bidirecional do MVP pronta e nativamente preparada para expansões futuras imediatas, tais como chats interativos em tempo real para discussões clínicas síncronas entre o Solicitante e o Especialista.

## Consequências

### Pontos Positivos (Ganhos)
* **Cumprimento Integral do Edital:** A atualização dinâmica da tabela de teleconsultorias e o disparo de alertas visuais acontecem de forma instantânea sem requisições forçadas de recarregamento na página.
* **Eficiência de Rede e Servidor:** Após o aperto de mão inicial (*handshake* HTTP), a conexão WebSocket permanece aberta usando um cabeçalho extremamente leve, economizando banda e processamento do servidor em comparação com requisições HTTP tradicionais.
* **Experiência do Usuário (UI/UX) Superior:** Reduz drasticamente o atrito operacional dos profissionais de saúde da APS, que recebem o feedback visual do parecer de forma fluida na linha de frente do atendimento.

### Pontos Negativos (Custos / Trade-offs)
* **Complexidade Arquitetural no Backend:** Obriga a transição do ecossistema de deploy do Django de WSGI (síncrono) para ASGI (assíncrono), exigindo servidores de aplicação especializados (como o Daphne ou Uvicorn) para rodar o backend.
* **Adição de Dependência na Infraestrutura:** Exige a inclusão e orquestração de um contêiner adicional do **Redis** no arquivo `docker-compose.yml` para atuar como gerenciador dos canais de comunicação (*Channel Layer*), elevando marginalmente o consumo de recursos de infraestrutura local do MVP.
* **Gerenciamento de Estado de Conexão:** O frontend Next.js precisa tratar cenários de quedas abruptas de rede através de lógicas de reconexão automática estáveis (*heartbeat/reconnection loops*), evitando o vazamento de memória ou a perda de sincronismo de dados em tempo de execução.
