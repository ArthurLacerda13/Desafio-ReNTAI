# 4. Mecanismo de Autenticação e Autorização com JWT e Controle de Acesso Baseado em Perfis (RBAC)

## Status
Pendente

## Contexto
O Módulo de Teleconsultoria lida com o trâmite de informações clínicas e cadastrais altamente sensíveis vinculadas ao Sistema Único de Saúde (SUS), o que impõe a obrigatoriedade de conformidade com os preceitos de privacidade e segurança regulamentados pela LGPD (conforme RNF008). 

Adicionalmente, os requisitos **RF001 (Cadastro de Usuários)**, **RF002 (Autenticação de Sessão)** e **RF003 (Controle de Acesso por Perfil - RBAC)** exigem uma segregação rígida e explícita das capacidades operacionais do sistema com base no papel do usuário autenticado:
* **Solicitante (APS):** Exclusividade na criação de teleconsultorias (`RF006`) e visualização de seus dashboards. Não pode acessar lógicas de pareceres.
* **Especialista:** Exclusividade no acesso a históricos clínicos de sua área e na emissão/registro de pareceres técnicos (`RF010`). Não pode visualizar botões de criação de casos.
* **Administrador:** Exclusividade no acesso aos logs brutos de auditoria da IA (`RNF005`), parametrização global do sistema e gerência de acessos.

Precisamos definir um mecanismo de autenticação que seja seguro, trafegue de maneira eficiente entre uma arquitetura desacoplada (Frontend Next.js e Backend Django API) e permita interceptar e validar as permissões de rota e recurso de forma performática.

## Decisão
Decidimos adotar a autenticação baseada em tokens **JWT (JSON Web Tokens)** acoplada a um modelo de **Controle de Acesso Baseado em Perfis (RBAC - Role-Based Access Control)**, implementando as seguintes diretrizes:

1. **Sessões Apátridas (Stateless) via JWT:** O backend Django não armazenará estados de sessão em memória ou banco de dados convencional para autenticação. Após o login válido, o servidor emitirá um par de tokens criptograficamente assinados: um *Access Token* (com tempo de expiração curto de 15 minutos) e um *Refresh Token* (armazenado de forma segura no cliente para renovação). O payload do token conterá a identificação do usuário e seu perfil explícito (`solicitante`, `especialista` ou `admin`).
2. **Segurança Multicamadas de RBAC:**
   * **No Backend (Django):** Criação de um *middleware* customizado de autorização ou uso de decoradores de permissão baseados no perfil injetado pelo token JWT nas requisições. Qualquer tentativa de requisição a um endpoint restrito (ex: `POST /api/pareceres/` por um Solicitante) será sumariamente bloqueada com um erro `HTTP 403 Forbidden`.
   * **No Frontend (Next.js):** Implementação de rotas protegidas por meio de *Middlewares* nativos do Next.js que analisam o perfil do token antes de renderizar as páginas. Lógicas reativas ocultarão ou exibirão componentes visuais específicos (como os botões de ação e abas do dashboard) dinamicamente baseadas nas permissões atribuídas.

### Alternativas Descartadas
* **Autenticação Padrão por Sessão do Django (Session-Based / Cookies):** Descartada por ser inerentemente *stateful* (exige consultas constantes à tabela de sessões do banco de dados) e por criar um acoplamento desnecessário, dificultando o deploy e o isolamento completo do Next.js como uma Single Page Application (SPA) distribuída autonomamente via Docker.
* **Protocolos Completos de OAuth2 / OpenID Connect (ex: Keycloak externo):** Embora ofereçam segurança corporativa exemplar, foram descartados por adicionarem uma camada massiva de complexidade de infraestrutura, configuração e desenvolvimento de endpoints que ultrapassa o escopo e o tempo disponível para a entrega do MVP deste desafio técnico.

## Consequências

### Pontos Positivos (Ganhos)
* **Alta Performance e Desacoplamento:** O backend valida a autenticidade e as permissões do token JWT de forma matemática e isolada (verificação da assinatura da chave pública/privada), eliminando a necessidade de bater no banco de dados PostgreSQL a cada requisição de API.
* **Cumprimento Estrito da LGPD:** Garante o princípio do privilégio mínimo. Um profissional da APS ou um invasor em potencial jamais conseguirá interceptar dados de especialidades ou auditorias sem possuir as credenciais e assinaturas de token adequadas.
* **UX Fluida:** O Next.js intercepta o perfil de acesso imediatamente no carregamento, impedindo oscilações visuais na tela (*flickering*) ao esconder elementos restritos antes mesmo de a página ser desenhada para o usuário.

### Pontos Negativos (Custos / Trade-offs)
* **Complexidade no Gerenciamento do Ciclo de Vida do Token:** Exige que o frontend Next.js gerencie ativamente a lógica de interceptação de erros HTTP (especialmente erros `HTTP 401 Unauthorized`) para disparar o fluxo assíncrono de atualização do token (*refresh loop*) sem interromper a experiência do usuário.
* **Invalidação de Tokens:** Como os tokens JWT são apátridas, revogar o acesso de um usuário imediatamente antes do tempo de expiração do *Access Token* (em caso de bloqueio administrativo, por exemplo) exige lógicas adicionais complexas, como uma lista de bloqueio temporária (*denylist*) mantida no Redis.
