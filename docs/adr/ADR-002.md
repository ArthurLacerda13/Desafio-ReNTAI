# ADR-002 - Estratégia de Persistência e Auditoria da Triagem de IA com PostgreSQL

## Status
Aceito

## Contexto
O Módulo de Teleconsultoria lida com dados sensíveis de saúde de pacientes do Sistema Único de Saúde (SUS), exigindo conformidade estrita com a Lei Geral de Proteção de Dados (LGPD). Isso impõe a necessidade de transações robustas (ACID) para garantir a integridade dos prontuários e históricos clínicos (conforme RNF007). 

Além disso, o requisito **RNF005 (Rastreabilidade e Auditoria de IA)** estabelece que, para cada validação de documento realizada pela Inteligência Artificial, o sistema deve obrigatoriamente persistir quatro parâmetros:
1. O score de confiança obtido.
2. O provedor do serviço de IA utilizado.
3. O limiar (*threshold*) ativo no momento da validação.
4. O *timestamp* exato da requisição.

O desafio consiste em estabelecer uma modelagem de persistência que blinde a integridade referencial das informações de saúde e, simultaneamente, ofereça uma estrutura maleável para estocar os logs e payloads brutos da Inteligência Artificial, evitando a necessidade de migrações (migrations) constantes no esquema.

## Decisão
Decidi adotar o **PostgreSQL** como o Sistema Gerenciador de Banco de Dados Relacional (SGBDR) central, utilizando uma abordagem híbrida de modelagem:

1. **Modelagem Relacional Tradicional:** Entidades principais estruturadas com tabelas bem definidas e chaves estrangeiras fortes (`users`, `teleconsultas`, `perfis`, `anexos`) para assegurar consistência e integridade referencial.
2. **Campos Especiais JSONB para Auditoria de IA:** Utilização do tipo de dado nativo `JSONB` do PostgreSQL para acoplar os dados obrigatórios de auditoria de IA (score, provedor, limiar e timestamp) e o payload bruto completo retornado pela API de triagem inteligente.

### Alternativas Descartadas
* **Bancos de Dados NoSQL Puros (ex: MongoDB):** Foram descartados porque, embora ofereçam excelente flexibilidade para os logs e respostas da IA, falham em fornecer nativamente os mecanismos rígidos de integridade referencial, restrições (*constraints*) e chaves estrangeiras que um fluxo crítico de prontuário médico e segundas opiniões clínicas exige.
* **MySQL / MariaDB:** Descartados devido ao fato de o PostgreSQL possuir uma implementação de dados semiestruturados (`JSONB`) substancialmente mais madura, performática e passível de indexação avançada (como índices GIN), o que otimiza buscas futuras por parte do perfil Administrador nos logs de auditoria.

## Consequências

### Pontos Positivos (Ganhos)
* **Garantia de Integridade (ACID):** Total segurança transacional na abertura, trâmite e encerramento de teleconsultorias, blindando o sistema contra corrupção de dados clínicos sensíveis.
* **Flexibilidade na Auditoria de IA:** O uso de campos `JSONB` permite cumprir os 4 parâmetros obrigatórios do edital e ainda guardar todo o histórico estruturado da IA. Se o provedor de IA for substituído (atendendo ao RNF004) e o formato do payload mudar, o banco de dados não precisará sofrer alterações de esquema (*migrations*).
* **Alta Performance em Consultas:** Capacidade de criar índices especializados (GIN) dentro do campo JSON, permitindo que o Administrador realize buscas rápidas no painel de auditoria por logs de um provedor específico ou scores abaixo de determinado limiar.

### Pontos Negativos (Custos / Trade-offs)
* **Complexidade em Queries do ORM:** O mapeamento e a escrita de consultas no Django ORM que filtram propriedades internas de campos JSONB são ligeiramente mais complexos e exigem sintaxes específicas do ecossistema Python/Django.
